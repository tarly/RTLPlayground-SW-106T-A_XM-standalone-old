# Iteration V0.2.6 — LED fix

## Goal

Make every front-panel LED follow the correct physical port, with no LED on when
no link is present.

## Root cause

The first LED investigation produced misleading results because the build
script had commented out the `leds_setup()` call in `rtlplayground.c`. The
backup used by that script was also contaminated, so several images were built
without LED-engine initialisation.

Symptoms of the bad builds:

```text
LED_PORT_SET_SEL = 0x00000000
LED set tables = reset/default values
port 3/4 steady on with no link
ports 1/2/5/6 no reaction
```

After restoring `leds_setup()` and rebuilding:

```text
LED_PORT_SET_SEL = 0x00010040
```

the LED engine started from a valid baseline.

## Investigation

1. Confirmed the baseline with `leds`.
2. Used `ledpad 0..27` one pad at a time with a link on port 1.
3. Built a pad table.
4. Reordered `led_mux` from that table.
5. Tuned `port_led_set` and `LED_GLB_ACTIVE` until no-link was all off and each
   port drove its own LED.

Unused pads: `0x3f`.

## Final configuration

```text
port_led_set = {0,0,0,3,2,2,0,0,3}
LED_PORT_SET_SEL = 0x00030ac0
LED_GLB_IO_EN = 0xffffffff
LED_GLB_ACTIVE = 0x3fffffff
```

## Final behaviour

| State | LED |
|---|---|
| No link | all off |
| Port 1 | 1 green blink |
| Port 2 | 2 green blink |
| Port 3 | 3 green blink |
| Port 4 | 4 amber blink |
| SFP5 | 5 blue blink |
| SFP6 | 6 blue blink |

**Correction:** an earlier draft listed the port 4 LED colour as an issue. That
was wrong. Port 4 is amber on this unit and the behaviour is correct. PCB
revisions may use another colour; colour is board-specific.

## Notes

- 1 amber was previously believed dead. `ledpad 3` proved it works.
- Stock firmware flashes all LEDs at power-on. This is a bootloader/early-init
  self-test, not `LED_MODE` bit 17. It is not reproduced by the final firmware.
- The final image is 512 KB; no 4 MB padding.
